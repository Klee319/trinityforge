# ステータスの「発動条件」をどう見せるか — 設計案 (2026-07-26)

## 課題（原文）

> 現状ステータスを総合ステータス参照で利用することで装備に任意の効果追加やステータスの加算が
> できるようにしている。これはアイテム作成の自由度が高いため崩したくない。ただしノックバックや
> 採掘時経験値上昇などのように発動条件を絞りたい時もあれば常時発動してもよいものもある。
> どうすればプレイヤー、editorともにUX/UIを担保できるだろうか。

---

## 1. 問題の正体 — 2つの軸が混ざっている

今「発動条件」と呼んでいるものは、**性質の違う2つの軸**が1語に潰れている。

| 軸 | 問い | 現状 |
|---|---|---|
| **供給元（source）** | その数値は**どの装備から**集まるのか | 全装備から合算（＝自由度の源泉） |
| **発動条件（trigger）** | その数値は**いつ**効くのか | **消費側のコードにベタ書き。configにもUIにも一切現れない** |

**崩したくないのは「供給元」の自由度**であって、「発動条件」ではない。
ブーツに `melee-knockback` を付けたら近接攻撃が強くなる — これは壊してはいけない。
壊れているのは「**その値がいつ効くのか、誰にも見えない**」ことの方。

この2軸を分ければ、自由度を1ミリも削らずにUXを直せる。

### 現状の実害（今日ある問題）

1. **無言で何も起きない組み合わせが作れる。**
   `item-cooldown` や `durability` は「そのアイテム自身の値だけ」を読む**アイテム固有キー**で、
   合算されない。ヘルメットに `item-cooldown` を書いても**警告もエラーも出ず、ただ何も起きない**。
   （`StatVocabulary` のコメントに「item専用キーは対象外」と書かれているが、
   **その事実がconfigにもeditorにも表現されていない**）

2. **プレイヤーが装備を比較できない。**
   ロアに「採掘幸運 +15%」と出ても、それが常時なのか、ツルハシを持っている時だけなのか、
   採掘した瞬間だけなのかが読み取れない。

3. **設計判断がコードにしか無いので、あなたが確認できない。**
   今セッションだけでも「近接専用のノックバック／スタンが Ars魔法に乗っていた」という
   条件漏れバグが実際に出た。宣言が無いので、レビューでしか見つからない。

---

## 2. 提案 — `stats/lore.yml` に2フィールド足すだけ

**新しい設定ファイルもレジストリも作らない。** `stats/lore.yml` は既に
ステータスごとの定義（表示名・アイコン・書式・小数桁・並び順・カテゴリ）を持っていて、
**プレイヤーのロア表示と editor のステータス選択の両方を駆動している**。ここが唯一の正しい置き場所。

### 現状のエントリ

```yaml
  crit-chance:
    name: 会心率
    format: PERCENT
    decimals: 0
    order: 3
    category: attack
```

### 提案するエントリ

```yaml
  crit-chance:
    name: 会心率
    format: PERCENT
    decimals: 0
    order: 3
    category: attack
    source: aggregate      # ← 追加: どこから集まるか
    trigger: attack        # ← 追加: いつ効くか
```

### `source`（供給元）— 3値の閉じた語彙

| 値 | 意味 | 該当キーの例 |
|---|---|---|
| `aggregate` | **既定**。防具・メインハンド・オフハンド・パーク・アドオンを全部合算 | ほぼ全部 |
| `item-local` | **そのアイテム自身の値だけ**を読む。合算されない | `item-cooldown` / `durability` / `tool-enchant-efficiency` |
| `mainhand` | 合算はするが、**メインハンドに持っている物由来の分だけ** | `gathering-efficiency` の適用先など |

**これは新しい仕様ではなく、今のコードの実態をそのまま書き起こしたもの。**

### `trigger`（発動条件）— 行為の種類

| 値 | 意味 | 該当キーの例 |
|---|---|---|
| `always` | 常時 | `max-health` / `damage-reduction` / 各種守備力 |
| `melee` | 近接攻撃時 | `melee-knockback` / `stun-chance` / `power-attack-*` |
| `ranged` | 弓・クロスボウ発射時 | `bow-accuracy` / `arrow-*` / `distance-damage-bonus` |
| `magic` | 魔法詠唱時 | 魔法が読む7キー |
| `attack` | 攻撃全般（近接・遠隔・魔法すべて） | `crit-chance` / `penetration` / `fixed-damage` |
| `defend` | 被弾時 | `dodge-chance` / `reflect-*` |
| `mining` / `woodcutting` / `farming` / `fishing` | その採取行為の最中 | `mining-fortune` / `fishing-luck` / `harvest-extra-drop-chance` |
| `craft` | クラフト・儀式時 | `workbench-quality-bonus` / `ritual-quality-bonus` |
| `on-kill` | 討伐した瞬間 | `mob-drop-bonus` / `kill-vanilla-exp-bonus` |

**これも今のコードの実態の書き起こし。** 例えば `mob-drop-bonus` が `on-kill` なのは、
`NativeSurvivalPerkListener#onDeathDrops` が `EntityDeathEvent` でしか読まないから。

> ℹ️ `trigger` は**供給元を1ミリも制限しない**。`melee` のステータスをブーツに付けたら、
> 近接攻撃時にちゃんと効く。今までどおり。変わるのは「見えるようになる」ことだけ。

## 3. プレイヤー側 UX

ロアの行頭に **trigger のアイコン**を出す。`lore.yml` には既に `icon` フィールドがあるので、
仕組みとしては新規実装ではなく**アイコンの出し分けを1段足すだけ**。

```
【Master】 Score→ 842

  ⚔ 会心率        +12%      ← 攻撃時
  ⛏ 採掘幸運      +15%      ← 採掘時
     守備力       +24       ← 常時（アイコンなし＝常時）
  ✋ アイテムCT    1.4秒     ← 手に持っている間
```

**設計のポイント: 「常時」だけアイコンを出さない。**
全部にアイコンを付けると視覚ノイズになる。常時が既定であり大多数なので、
**条件が付いているものだけを目立たせる**方が読みやすい。

- 凡例は `/tf help` か、装備を持ってのツールチップ末尾に1行だけ
- 同じ trigger の行を**隣り合わせに並べる**（`order` の中で trigger 別にグルーピング）と、
  「この装備は採掘特化」「この装備は近接特化」が一目で分かる

## 4. editor 側 UX

### 4-A. ステータスを選ぶ時にバッジを出す

今セッションでステータス選択に**カテゴリフィルタ**が付いた。同じ場所に trigger バッジを出す。
`lore.yml` を読むだけなので、**新しいデータ源は不要**。

```
[ 攻撃 ▾ ]  検索: ____

  ⚔近接  ノックバック強化
  ⚔近接  スタン確率
  ⚔攻撃  会心率
  ⛏採掘  採掘幸運
  ✋所持  アイテムCT
```

### 4-B. 「何も起きない組み合わせ」を警告する ← **これが最大の価値**

`source: item-local` のキーを、そのアイテム自身が使わない場所に書いた時に警告を出す。

> ⚠️ **アイテムCT** は「そのアイテムを手に持っている時」にだけ働きます。
> ヘルメットに設定しても効果がありません。

**今日いちばん危険なのは、間違いが無言で通ることです。** これを潰すだけで体感がかなり変わる。

同様に、**明らかに噛み合わない組み合わせ**にも情報レベルの注記を出せる:

> ℹ️ **弓の命中精度** は弓・クロスボウを撃った時にだけ働きます。
> この胸当てに付けても、装備している限り合算されるので有効です。

（＝**禁止ではなく説明**。自由度を削らないための線引き）

### 4-C. アイテムの「性格」をまとめて見せる

アイテム編集画面の上部に、そのアイテムが持つ trigger の内訳を出す。

```
このアイテムの効果: ⚔近接 3 / ⛏採掘 2 / 常時 4
```

「近接装備のつもりが採掘ステが混ざっている」といった設計ミスに、保存前に気付ける。

## 5. 「同じステでも条件を変えたい」場合（任意・第2段）

§2 までで**大多数は解決する**が、「このツルハシの採掘幸運はスニーク中だけ」のような
**アイテム個別の絞り込み**をやりたくなった場合の拡張余地。

`item-stats.yml` のエントリ側に**任意の `when:`** を許す。

```yaml
  DIAMOND_PICKAXE#1001:
    fixed:
      mining-fortune: 20
    when:
      mining-fortune: sneaking   # 既定(mining)をさらに絞る
```

**制約: 絞ることしかできない（広げられない）。**
`lore.yml` の trigger より広い条件は書けない。こうしないと、
「どの装備がいつ効くのか」の全体像が崩れて §3・§4 の説明が成立しなくなる。

**私の推奨は、これは今やらないこと。** §2〜§4 を先に入れて、実際に「絞りたい」場面が
何回出てくるかを見てから判断するのが安全。条件が増えるほどプレイヤーの理解コストが上がるので、
**入れないで済むならそれが一番良い。**

## 6. 宣言と実装がズレないようにする

この案の弱点は「`lore.yml` に書いた条件が、実際のコードの挙動とズレる」こと。
今セッションの「近接専用ステが魔法に乗っていた」バグが、まさにそのズレだった。

対策を2つ。

1. **全キーに `source` / `trigger` があることを強制するテスト。**
   `StatVocabulary` に載っているキーで `lore.yml` に宣言が無いものがあればビルドを落とす。
   このプロジェクトは既に「静かに壊れるより騒がしく落ちる」ガードを採用している
   （`ActiveSkillCooldownKeys.verifyRegistered` が同じ思想）ので、流儀としても一貫する。

2. **`trigger` ごとに「読んでよい消費者」を1本のテストで固定する。**
   例: `trigger: melee` のキーは `MELEE_CAUSES` ゲートの内側でしか読まれない、を機械的に検査する。
   今回のバグはこれがあれば発生時点で落ちていた。

**enforcement（コード側で範囲外のステを実際に0にする）はやらないことを推奨。**
自由度を削るリスクが高く、既存装備の挙動が変わる。**宣言＋UI＋ドリフト検査**で十分に目的を達する。

---

## 7. 実装の規模と順序

| 段 | 内容 | 規模 | 効果 |
|:--:|---|---|---|
| **1** | `lore.yml` に全キーの `source` / `trigger` を書く（実態の書き起こし） | 小（設定のみ） | これ単体で**あなたが全体像を把握できる**ようになる |
| **2** | editor: バッジ表示 + item-local の警告（§4-A / 4-B） | 小 | **無言で何も起きない事故が消える** |
| 3 | ロアに trigger アイコン（§3） | 小〜中 | プレイヤーが装備を比較できる |
| 4 | ドリフト検査テスト（§6） | 小 | 条件漏れバグの再発防止 |
| 5 | editor: アイテムの性格サマリ（§4-C） | 小 | 設計ミスに保存前に気付ける |
| — | 個別 `when:`（§5） | 中 | **推奨しない。必要になってから** |

**段1と段2だけで、課題のほとんどは解決する。** どちらも既存の器に乗るのでリスクが低い。

---

## 8. あなたに決めてほしいこと

1. **この2軸（source / trigger）の分け方で腹落ちするか。**
   「崩したくない自由度」＝ source、「絞りたい条件」＝ trigger、という整理で合っているか。

2. **`trigger` の語彙（§2の表）に過不足はないか。**
   今は既存コードの実態から起こしたので、「本当はこう分けたい」があれば今のうちに。

3. **段1〜2だけ先に入れるか、段3〜4までまとめてやるか。**
   → 私の推奨は**段1・2を先に入れて実際に触ってみる**。表示の細かい好み（アイコンを出す/出さない、
   凡例の置き場所）は、実物を見ないと決まらないため。

4. **§5（アイテム個別の絞り込み）は保留でよいか。**
   → 私の推奨は保留。

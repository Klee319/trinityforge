# 予告機構 実装仕様（必須6機構）

`docs/design/2026-08-31-dungeon-concept-rework.md` が「これが無いと設計そのものが成立しない」とした
6 つの機構を、実コードへ落とせる粒度まで詰めたもの。**設計の意図は正本側にあり、ここは実装契約だけを書く。**

対象は TF 本体のみ。フォーク側（EliteMobs / ArsPaper）に技・詠唱・回避の独自実装があるかは
**未確認**なので、着手前に `fork-handoff/` を明示指定した検索を 1 回走らせる
（`.gitignore` 除外のため通常の検索では消える）。

## 全体の順序

1〜6 は依存関係の順に並んでいる。**1 を飛ばして 3 を作ると、描いた輪が判定と食い違ったまま出荷される。**

## 機構 1 — 範囲判定を円へ直す

### 現状

被害判定は `MobAbilityExecutor#playersNear(Location, double)` に集約されているが、実体は
`world.getNearbyEntities(center, r, r, r)` の**軸並行の箱**である。呼び出し元は
`groundSlam` / `charge` の着地判定 / `aura` / `repulse` / `vortexPull` / `delayedZone` の 6 箇所。

**`beam` だけはこの関数を通らず、1m 刻みの各点で `getNearbyEntities(cursor, t, t, t)` を自前で呼ぶ。**
斜めのビームでは箱が数珠つなぎになるため、**太さが方向によって波打つ**。

### 仕様

新クラス `combat/AbilityShapes` を作り、**判定と描画の両方がここから座標を得る**。Bukkit 依存は
座標型だけに留め、幾何の本体は純関数にする（MockBukkit が粒子を記録しないため、テストは純関数に当てる）。

```
boolean hitsCircle(Location center, double radius, double verticalRadius, Location target)
boolean hitsLine(Location from, Vector dir, double length, double thickness, Location target)
List<Vector> ringOffsets(double radius, double spacing)
List<Vector> lineOffsets(Vector dir, double length, double step)
```

- **円**: `dx*dx + dz*dz <= radius*radius` かつ `|dy| <= verticalRadius`。
  水平と垂直を分ける。今は垂直にも `radius` が効いており、半径 6 の技は**上下 6 ブロックにも当たる**。
- **`vertical-radius` の既定は 3.0** とし、テンプレートで上書きできるようにする。
  `radius` へフォールバックしない。フォールバックすると今の理不尽がそのまま残る。
  3.0 は「同じ床にいる」を表す値で、段差 1〜2 ブロックは拾い、上の階は拾わない。
- **直線**: 点から線分への垂直距離で判定する。`thickness` は半径として扱う。
  cursor ごとの箱判定はやめる。壁で止める挙動は現行どおり維持し、**止まった位置を線分の終点にする**。
- プレイヤー側の座標は**足元**（`player.getLocation()`）で測る。現行と同じ。

### 影響と後方互換

判定は**必ず狭くなる方向**へ動く（箱→円で対角がなくなり、垂直が 3.0 に縮む）。
半径 4 の技は対角で約 5.7 ブロックまで当たっていたので、**体感難易度が下がる**。

`mob-abilities.yml` の `radius` 値は**据え置きで出す**。円化した状態の実測を取ってから調整する。
先に数値をいじると、円化の効果と数値調整の効果が混ざって切り分けできない。

### テスト

- `ringOffsets` の全点が `hitsCircle` の境界上にあること（内外の判定が輪と一致すること）。
- 半径 4 の円で、45 度方向 5.0 ブロックの点が**外れる**こと（箱時代の回帰）。
- 斜め 45 度のビームで、太さが軸方向と同じであること。
- いずれも Bukkit 非依存で書ける。`getNearbyEntities` が MockBukkit の実 `WorldMock` で動くかは
  未確認なので、**候補収集のラッパーは差し替え可能にしておく**。

## 機構 2 — `cast-seconds` と詠唱中の向き固定

### 追加するフィールド

`MobAbility` に 3 つ足す。既存の旧 arity コンストラクタ互換パターン（`healthBelow` 追加時の実績）を踏襲する。

| キー | 型 | 既定 | 丸め | 意味 |
|---|---|---|---|---|
| `cast-seconds` | double | 0.0 | 0.0、または 0.5〜2.5 | 予告時間。0 は「予告なし＝現行どおり即時」 |
| `lethal` | boolean | false | — | 致命予告かどうか。**予告予算の枠を決める**。最終ダメージでは判定しない |
| `vertical-radius` | double | 3.0 | 0.5〜8.0 | 機構 1 の垂直判定 |

`0 < cast-seconds < 0.5` は **0.5 へ切り上げる**。書き間違いで「予告付きのつもりの回避不能技」に
化けるのを防ぐ（`delayed_zone` の `duration-seconds` が同じ思想で 0 を禁じている）。

`new MobAbility(...)` の呼び出しは本体に 2 箇所（パーサとテスト 1 本）しかないので、追加コストは小さい。

### `duration-seconds` との関係

`delayed_zone` の `duration-seconds` は「印を置いてから着弾まで」で意味が同じ。統合はしないが、
**`cast-seconds` 未指定なら `duration-seconds` を予告時間として読む**（後方互換）。
両方書いてある場合は `cast-seconds` を優先し、**読み込み時に 1 回だけ警告する**。

### 実行の流れ

`MobAbilityExecutor#execute` を 2 経路にする。

- `castSeconds <= 0` → 現行どおり即時解決。**396 体の雑魚の挙動は 1 ミリも変わらない。**
- `castSeconds > 0` → 詠唱オブジェクトを作り、**1 tick 間隔**の `BukkitRunnable` を回す。

詠唱ループが毎 tick やること:

1. **向きを固定する。** 開始時の yaw/pitch へ書き戻す。`setAI(false)` は使わない
   （移動ごと止めると突進系が壊れ、見た目も死ぬ）。**向きだけ**を毎 tick 戻す。
   モブの AI が毎 tick 向きを上書きするので、5 tick 間隔では固定できない。
2. **5 tick ごとに**予告演出（機構 3）とアクションバー更新（機構 4）を出す。演出は間引く。
3. 中断条件（次段階の機構）を見る。この仕様では枠だけ用意し、判定は入れない。

詠唱の終わりにやること:

1. **主対象を再確認する。**死亡・退出・ワールド変更・**視線が切れた**のいずれかなら**不発**にする。
   不発はイベントとして出し、アクションバーへ 0.8 秒表示する。
2. 通れば型ごとの解決処理を呼ぶ。以降は現行と同じ。
3. 成否にかかわらず**予告予算を解放する**（機構 5）。

術者が詠唱中に死んだ場合は不発。現行の `delayedZone` が既に同じ扱いをしている。

### editor 側

キーを 3 つ増やすと、editor は 4 箇所を直す必要がある。

- `tools/config-editor/lib/schema.js` の `MOB_ABILITY_RANGES`（Java の丸めを手で複製している表）
- `public/js/mob-abilities-form.js` の `NUMERIC_BOUNDS`（同じ表の 2 本目）
- 同ファイルの `FIELD_LABELS` / `FIELD_DESCS`
- 型限定で出すなら `FIELDS_BY_TYPE`

**この 2 本の範囲表が Java の丸めとズレると、「エディタで開いて保存しただけで yml の意味が変わる」。**
過去に同種の事故がある。ズレは条件が緩む方向に出るので気づけない。

### 網羅テストを 1 本足す

現在、**MobAbility のフィールドが yml → schema → form の 3 層に揃っているかを照合するテストが無い。**
この機会に足す。許可リスト方式（キー名を手で列挙する）にすると、リスト自体が誤ったときに
検査ごと無効化されるので、**出荷 `mob-abilities.yml` に実在するキーを列挙して**
schema と form が全部知っているかを突き合わせる形にする。

## 機構 3 — 予告レンダラ

### 既にあるもの

`progression/ParticleGeometry` に**輪郭のみの円**が実装済みで、`circleOffsets(count, radius)` が
円周座標を返す形で公開されている。Bukkit 非依存の純関数。**これを使う。新規に書かない。**

直線用の形は無いが、`beam` 自体が既に「1m ずつ進めて演出を出す」ループを持っているので、
そのループを機構 1 の `AbilityShapes` へ寄せれば判定と描画が自然に共有される。

### 仕様

| 技の分類 | 予告の形 |
|---|---|
| 円形・固定地点・固定領域 | 判定半径ちょうどの**輪郭だけ**。内側は塗らない |
| 直線 | 射線上に 1m 刻みの点。**壁で止まる位置まで**（判定と同じ） |
| 引き寄せ・吹き飛ばし | 術者から**各被害者**への線 |
| 追従領域 | 術者中心の輪郭＋術者への線 |

- **粒子の上限**: 輪は 1m あたり 2 個（= 0.5m 間隔）。円周の点数は `ceil(2πr / 0.5)` で求め、
  **64 点で頭打ち**にする。統合版は描画距離が短く、盛ると自分の足元が見えなくなる。
  `ParticleGeometry` 側に上限は無いので、`AbilityShapes` 側で丸める。
- **予告と着弾で別の演出を使う。**予告は輪、着弾は現行の `playEffects`（塊）。
  今は同じ関数を通っているので「予告中」と「今当たった」が区別できない。
- 粒子の**種類**は現行の割り当てを踏襲する（炎・氷・光条・爆発・転移・腐蝕）。
  色を指定できる型は実装が弾くので、**色はアクションバーの文字で表す**（機構 4）。

### テスト

MockBukkit は `spawnParticle` の呼び出しを記録しない。したがって、
**「輪が正しく出たか」は JUnit では検証できない。**座標生成の純関数に対して

- 輪の点が全部 `hitsCircle` の境界上にあること
- 点数が上限で丸められること
- ビームの点が壁で止まること

を固定し、**見た目の検証は実機（後述の検証アダプタ）へ回す。**

## 機構 4 — アクションバー予告と、既存機能との調停

### 先に解決すべき衝突

**アクションバーは既に使われている。**とくに戦闘スキルの EXP 獲得表示は、設定次第で
獲得のたびに `+N EXP` をアクションバーへ出す。**ダンジョン戦闘中は常時発火する。**
0.25 秒ごとに更新する予告バーと真正面から殴り合い、どちらも読めなくなる。

他にも装備レベル不足の警告、AFK 警告、各種ゲートの警告が同じ場所を使っている。
こちらは単発トリガーなので頻度は低いが、予告と重なれば予告を隠す。

### 仕様

**調停役を 1 つ作る**（`ActionBarRouter`）。全プレイヤーぶんのアクションバーを一元管理する。

優先度（高い順）:

1. 予告（致命）
2. 予告（通常）
3. 中断成功・不発・空振り硬直の通知（0.8 秒）
4. 警告（装備レベル不足など）
5. スキル EXP 表示
6. AFK 警告

- **予告が走っている間、EXP 表示は捨てる。**溜めて後から出さない
  （戦闘が終わってから EXP が滝のように流れるほうが邪魔になる）。
- 予告が 2 本走っている場合、**致命を優先**。同じ重さなら着弾が近い方を出し、末尾に `+1` を添える。
  **「着弾が近い方」を単独の基準にしない。**軽い予告が近いという理由で致命予告を隠すと、
  予告予算を設けた意味が消える。
- 表示形式は `<色>技名 ▮▮▮▯▯</色>`。バーは**5 段固定**（残り時間を 5 等分）。
  統合版の文字幅を考え、**技名は全角 6 文字以内**に揃える。既存 21 テンプレートの名前を確認して直す。
- 色は正本の 5 色規約（赤＝離れる／金＝退く／紫＝横へ／水＝遮蔽／緑＝止める）に従う。

### 移行の範囲

`sendActionBar` の呼び出しは本体に 40 箇所を超える。**全部を一度にルータ経由へ移さない。**

- 第 1 段階: **予告とスキル EXP 表示の 2 つだけ**をルータ経由にする。ここが実害の 9 割。
- 第 2 段階以降: 警告・AFK を順次移す。単発なので急がない。

### テスト

MockBukkit は `sendActionBar` を観測できる（既存テストに実績がある）。したがって
**優先度の調停は JUnit で完全に検証できる。**

- 予告中に EXP 表示を投げても、アクションバーは予告のままであること
- 致命と通常が同時なら致命が出て、末尾に `+1` が付くこと
- 予告が終わったら EXP 表示が復帰すること

## 機構 5 — 予告予算

### 仕様

新クラス `TelegraphBudget`。`MobAbilityCooldowns`（モブ UUID キー）とは**別の台帳**で、
**プレイヤー UUID をキー**にする。

```
Map<UUID /* player */, List<ActiveTelegraph>>
ActiveTelegraph { abilityId, lethal, resolveAtTick, casterUuid }
```

- **単位はプレイヤー。**「部屋」や「戦闘グループ」を単位にしない。
  インスタンスワールドは入場のたびに名前が変わり、座標領域の切り方も決まらないので、
  キーが定義できない。プレイヤー単位なら定義が一意になる。
- **上限は致命 1 本・合計 2 本。**
- **予約は詠唱開始時**に取る。取れなければその技は撃たない。
- **解放は次の全部**: 解決・不発・中断・術者の死亡・対象の退出／死亡／ワールド変更・ワールドのアンロード。
  現行の `delayedZone` は非同期タスクを始めて即座に成功を返すので、
  **そのタスク自身に登録と解除の責務を持たせる**（外から追跡できない）。
- **数えるのは詠唱開始時点の主対象 1 人ぶんだけ。**範囲技の巻き添えは数えない。
  巻き添えが上限を超えうることは仕様として認め、4 人試験で実害を見る。
- 固定領域は**展開までを予告として数え、展開後は解放する**。領域が続く間ずっと枠を握らない。

### 抽選への差し込み

`MobAbilityTask#tryFire` は「候補収集 → ランダムに 1 つ選ぶ → その発動率を 1 回引く」という順序である。
予算チェックは**候補収集の段階**で行い、予約が取れない技を候補から外す。

**候補が全部落ちたらその抽選は空振りにする。**別の技へ振り替えない。振り替えると
「予算が埋まっているときほど軽い技が飛ぶ」という、設計意図と逆の挙動になる。

### テスト

- 3 本目の予告が抽選から外れること
- 致命が 1 本走っている間、2 本目の致命が撃たれないこと
- 術者が死んだら枠が解放されること
- 対象がログアウトしたら枠が解放されること
- 候補が全部落ちたときに別の技へ振り替わらないこと

## 機構 6 — 予告技へ確率回避を通さない

### 現状

回避は攻撃 1 回につき 1 度だけ、ダメージ計算の**冒頭**で引かれる。
物理と魔法の混成でも 1 回にまとめられている。**後段で打ち消す実装はできない。**

`DodgeResolver` はコンストラクタ注入ではなく、計算メソッドの中でその場で組み立てられている。

### 仕様

`telegraphed`（boolean）を、技の実行からダメージ計算の入口まで通す。

```
MobAbilityExecutor#applyHit
  → SymmetricCombatService#physicalFinalDamageFromMob
  → #physicalFinalDamageFromMobResult          （2 オーバーロード）
  → #componentResult / #hybridComponentResult  （非 hybrid / hybrid）
```

- **既存のシグネチャは残す。**`telegraphed = false` で新シグネチャへ委譲するだけにする。
  呼び出し元が他にもあるため、置換ではなくオーバーロード追加にする。
- 計算メソッドの中で `telegraphed ? DodgeResolver.NEVER : cappedDodge` を選ぶ。
  `DodgeResolver.NEVER` は既に定義されているので新設不要。
- `DefenderProfile` と計算パイプライン本体は無改修。

### 何を「予告付き」とみなすか

`castSeconds > 0` の技すべて。`delayed_zone` は `duration-seconds` 経由でも予告付きになる。
**通常攻撃と `castSeconds == 0` の技には従来どおり回避率が効く。**

### テスト

- 回避率 1.0 のプレイヤーへ予告付きの技を撃つと、必ずダメージが入ること
- 同じプレイヤーへ予告なしの技を撃つと、回避されること
- 通常攻撃の挙動が変わっていないこと（回帰）

## 検証アダプタ（debugMCP の TrinityForge 対応）

上の 6 機構のうち、**JUnit で検証できるものとできないものが明確に分かれる。**

| 機構 | JUnit で足りるか | 理由 |
|---|---|---|
| 1 円化 | **足りる**（幾何の純関数） | ただし候補収集の実挙動は実機が要る |
| 2 詠唱・向き固定 | 部分的 | 向き固定は実機でないと確かめられない |
| 3 レンダラ | **座標だけ** | 粒子の呼び出しが記録されないので見た目は不可 |
| 4 アクションバー | **足りる** | 観測できる |
| 5 予告予算 | **足りる** | 台帳の純ロジック |
| 6 回避非適用 | **足りる** | 計算の入出力 |
| 視線判定（次段階） | **不可** | 視線とターゲット取得が未実装で、テストが素通りする |

**視線判定・向き固定・見た目・そして正本の受入試験の大半は、実 Paper でしか測れない。**
`C:/Users/T-319/Documents/Program/ClaudeCodeDev/products/minecraft/debugMCP` の隔離テストサーバーが
その受け皿になるが、**現状は道路建設ドメイン専用**で TF の語彙を持たない。

### 足りないもの

土台（プロセス管理・loopback HTTP とトークン・連番付きイベント列・不変条件チェッカ・
シナリオ実行器・実ボット接続・本番キルスイッチ）は既にある。足すのは TF ドメインのアダプタだけ。

Bridge に足す口:

| 口 | 用途 |
|---|---|
| `spawn-mob` | モブ id・レベル・座標を指定して湧かせる |
| `set-player-stats` | 装備一式ではなく、合算後のステータスを直接差し替える（回避率 0 の統制に要る） |
| `fire-ability` | 技を**強制発動**する。ランダム抽選を待たない。これが無いと 20 回試験に何時間もかかる |
| `state/combat` | 直近 N 件のダメージを内訳つきで返す（物理／魔法・会心の有無・回避の有無・軽減の内訳） |
| `state/telegraphs` | 進行中の予告（技 id・致命か・残りtick・対象） |
| `assert-invariants` | 予告予算の上限、輪と判定の一致、回避非適用 |

MCP ツールに足すのは 3 本（`minecraft_spawn_mob` / `minecraft_fire_ability` / `minecraft_get_combat_state`）。
**任意コマンド実行の口は作らない**（既存の設計方針に従う）。

### 前提として先に片付けること

- `test-server/runtime/` が存在せず、`fixtures/` と `snapshots/` が空。
  この状態では高速リセットも完全リセットも動かない。
- Paper 1.21.11 本体が未配置（利用者が eula に同意したうえで置く）。
- Bridge のポートが 8765 に**固定**で、環境変数の上書き口が無い。
  この端末では既に別プロセスが掴んでいて起動できなかった。ポートを設定可能にする。
- MCP サーバーとして登録されていない。

### アダプタで測れるもの・測れないもの

**測れる（人間より正確）:** 判定が箱か円か（0 度と 45 度に立たせるだけ）／予告時間と実着弾時刻のズレ／
壁越し被弾／中断のしきい値／予告技に回避率が乗っていないか（回避率 1.0 で撃たせる）／
ダメージの内訳を 100 発単位で／出血の上書き／同時予告の本数。

**測れない:** 初見で何が起きたか分かるか／予告が見えるか／統合版での視認性／
対処が等価か／楽しいか。ボットの戦闘は雑なのでビルド別の討伐時間も低精度。

### 一番大事な区別

**ボットの 20 回試験は「幾何学的に避けられるか」を測るのであって、「人間に避けられるか」ではない。**
ボットは完璧に動く。

正本の三段構えでいうと、これは**一次（机上検査）を実測版へ格上げする**ものであって、
**二次（人間の 20 回試験）を消すものではない。**
ここを混同して「ボットが 18/20 通ったから合格」で出荷すると、実機で誰も避けられない技が出る。

## 2026-09-04 追記 — 第三者 UX レビューの反映

実装着手時に Codex による UX クロスレビューを受けた（原文と反映表は
`docs/design/2026-09-04-telegraph-ux-review-codex.md`）。本文の記述と食い違う場合は**この節が優先**する。

- **機構 2 の不発条件は型別**にする。主対象の視線再確認は「狙う技」（`beam` / `teleport_strike` /
  `projectile_volley` / `projectile_rain`）だけ。自分中心の技（`ground_slam` / `aura` / `repulse` /
  `vortex_pull`）と床印（`delayed_zone`）は視線を見ない（床印を「柱に隠れて消す」第2解を作らないため）。
- **幾何はスナップショット**。詠唱開始時に origin / dir / anchor / 壁で止めた終点を固定し、描画と解決の両方が
  同じスナップショットから出る。向きの書き戻しは残すが、実機でガクつきが不快なら外してよい（幾何には影響しない）。
- **直線の判定はプレイヤーの BoundingBox 中心**（足元ではない）。描画は中心線ではなく **±thickness の左右 2 レール**。
- **音は 3 段に分離**: 詠唱開始 1 回／着弾 5tick 前の共通合図音／着弾で従来の `playEffects`。予告フレームは無音。
- **アクションバーは行動語を先頭に置く**: `[横へ] 貫通光 ▮▮▮▯▯ 1.3s`。行動語は型から導出
  （離れろ／床から退け／横へ／遮蔽へ／止めろ）。予告が 0 本になったら空表示を 1 回送って残像を消す。
- **受信者**は主対象＋脅威圏内（判定関数で当たる位置にいる）＋anchor から水平 12m。半径 32 の一律告知は詠唱経路では使わない。
- **予算**は主対象を必須予約、脅威圏内の他プレイヤーはベスト・エフォート予約。
- **終端処理は 1 箇所**（`finish`）。二重呼び出しガード付きで、タスク停止・予約解放・全 viewer の表示終了・不発通知をまとめる。
- **見送り（設計側の残課題）**: 机上式の遅延補正（D95 実測後）、空振り硬直と技選択のリズム（後段の機構）、
  統合版の実機可読性検証（出荷前の必須項目。JUnit では測れない）。

# 定期再起動と軽量化

**方針**: 測ってから直す。効果が数字で出るものだけをやる。

---

## 1. 定期再起動

### 再起動プラグインを使わない

**HuskSync は restart 系プラグインを公式に非対応と明記している。**
プロセスを生かしたままワールドとプレイヤーを作り直す方式は、
「切断時に保存・接続時に読込」という HuskSync の前提を壊し、データ消失とアイテム複製の温床になる。

よって再起動は **RCON `stop` によるクリーンシャットダウン** で統一する。プラグインは増やさない。

### 構成

| 部品 | 役割 |
|---|---|
| [server-loop.cmd](scripts/server-loop.cmd) | `java -jar paper.jar` をループで囲み、`stop` 後に自動で起動し直す |
| [restart-server.ps1](scripts/restart-server.ps1) | RCON で 10/5/1 分前に予告 → `stop` → プロセス終了を待つ |
| FallbackRouter (Velocity) | 落ちたサーバの在席者をもう一方へ自動退避 |
| タスクスケジューラ | 日次で `restart-server.ps1` を起動 |

**Velocity 自体は落とさない。** 片方のバックエンドを再起動している間、
在席者はもう一方へ移動させられるだけで、ネットワークからは切断されない。
これがマルチサーバ構成の主な利点であり、単一サーバでは絶対に得られない。

### 強制終了しない

`restart-server.ps1` はタイムアウトしても **kill しない**。中断して通知するだけ。

理由: `plugins/TrinityForge` はジャンクションでメインと実体を共有しており、
その中の SQLite をフラッシュ途中で殺すと **両サーバの進行データを同時に壊す**。
「落ちないサーバ」は人間が見るべき異常であって、自動化で押し切るべきものではない。

### 推奨頻度と順序

| 対象 | 頻度 | 時刻の目安 |
|---|---|---|
| resource | 日次 | 早朝（例 05:00） |
| main | 日次 | 早朝（例 05:10） |

**資源 → メイン の順にずらす。** 同時に落とすと両方から追い出されてしまう。
`restart-server.ps1 -Target both` はこの順序と間隔（既定 90 秒）を内蔵している。

25 人規模なら日次で十分。ラグが溜まるのが早いようなら 12 時間ごとに増やす前に、
まず spark で原因を見ること（次章）。

## 2. 軽量化 — 測ってから直す

### spark は Paper 1.21 に同梱済み

追加インストールは不要。

```
/spark profiler start --timeout 300
/spark profiler stop
```

出力される URL をブラウザで開くと、どのプラグイン・どの処理が
メインスレッドを食っているかがフレームグラフで見える。

**移行の前後で必ず1回ずつ取る。** 2サーバ化の効果（特にチャンク生成負荷がメインから消えたか）を
数字で確認できる。これをやらないと「なんとなく軽くなった気がする」で終わる。

`/spark tps` と `/spark healthreport` も併用する。

### 無料で効く順

#### 1. Chunky の事前生成 — 今回の構成と最も相性がいい

チャンク生成はサーバで最も重い処理のひとつ。プレイ中に走らせないのが最善。

- メイン: ボーダー設定後に `radius 2500` を1回だけ事前生成すれば、以後ほぼ生成は起きない
- 資源: 毎週のリセット直後、誰も居ない時間帯に事前生成する
  （[reset-resource.ps1](scripts/reset-resource.ps1) が自動で開始する）

> 資源サーバの `pause-when-empty-seconds` を有効にすると tick が止まり、
> **事前生成も止まる**。両立しないので、既定は `-1`（無効）にしてある。

#### 2. `config/paper-world-defaults.yml`

数字を下げる前に spark でボトルネックを確認すること。効きやすい順:

| 項目 | 内容 |
|---|---|
| entity activation range | 遠くの Mob の思考を止める。Mob が多いワールドで効く |
| mob spawn limits | 湧き上限。**両サーバで同じ値にすること**（片方だけ緩いと行動が歪む） |
| `alt-item-despawn-rate` | 丸石・土などの despawn を早める。ドロップ品が溜まる資源サーバで効く |
| `max-auto-save-chunks-per-tick` | 自動保存のスパイクをならす |

#### 3. `view-distance` / `simulation-distance`

現在 10 / 6。既に控えめなので下げ幅は少ない。ここを削るのは最後。

#### 4. Hurricane（導入済み）

パケット最適化。すでに入っているので追加作業なし。

#### 5. 不要プラグインの棚卸し

**資源サーバから BlueMap と EliteMobs を外すこと自体が最大の軽量化**になる。
特に BlueMap は「毎週消えるワールドを毎回フルレンダーする」ので、
同一マシンで CPU を共有する構成では実質メインへの負荷になる。
詳細は [PLUGIN_MATRIX.md](PLUGIN_MATRIX.md)。

### ClearLag 系は入れない

症状を隠すだけで原因は残る。しかもプレイヤーが置いたドロップ品を消す事故を招く。
アイテムが多すぎるなら `alt-item-despawn-rate` とマージ設定で対応する。

## 3. 同一マシン 2 JVM のリソース配分

CPU: i7-13700K（16C / 24T）、RAM: 63.75GB。

| | ヒープ | 根拠 |
|---|---|---|
| Velocity | 1G | プロキシはほとんどメモリを使わない |
| main | 8G | 現状維持 |
| resource | 6G | ワールドが毎週新品でチャンクキャッシュが育たない。メインより少なくてよい |
| MariaDB + Garnet（ネイティブ） | 1.5G 程度 | Garnet は `--memory 1g` で上限を切る。**WSL2 構成にすると VM の分だけ余計に確保される** |
| **合計** | **約 17G** | 64GB に対して十分な余裕 |

### 正直に言っておくこと

**同一マシンでは CPU コアを共有するので、「負荷隔離」は完全ではない。**
メインスレッドと GC が別プロセスに分かれる効果は確実にあるが、
資源サーバでチャンク生成が走れば、その分のコアはメインから奪われる。

一方で**再起動の独立性はマルチサーバ構成でしか得られない**。
「資源サーバだけ再起動・リセットしてもメインは無停止」という運用上の価値は、
CPU 共有の不利を上回る。2サーバ化の判断自体は妥当。

将来もし完全に分離したくなったら、資源サーバを別マシンへ移すことになるが、
そのときは**ディレクトリジャンクション方式が使えなくなる**
（ネットワーク共有上の SQLite は破損する）。
その場合は `ProgressionRepository` に MariaDB 実装を足すことになる。
詳細は [RUNBOOK.md](RUNBOOK.md) の「将来の拡張パス」。

## 4. 移行前後の比較手順

1. **移行前**: メインで `/spark profiler start --timeout 300` を全盛時間帯に実行し、URL を控える
2. **移行後**: 同じ時間帯に同じコマンドをメインで実行
3. 比較する観点:
   - チャンク生成（`ChunkGenerate` 系）の割合が下がったか
   - GC pause の頻度と長さ
   - TPS の下限（`/spark tps` の 5m / 15m）
4. 資源サーバ側でも1回取り、想定どおり「チャンク生成が主な負荷」になっているか確認する

改善が見られない場合、負荷の原因は 2 サーバ化では解決しない場所（特定プラグインや Mob 密度）にある。
その場合は spark のフレームグラフから犯人を特定してから手を打つこと。

## 2. 戦闘バランスの構造的破綻 (HIGH・要設計判断)

ここは個別バグではなく**設計そのものの再検討が要る**領域です。

| ID | 内容 |
|---|---|
| **CMB-02 / MOB-02** | **player→eliteモブのダメージが二重に計算される**。TF汎用`CombatListener`とフォーク`TrinityForgeCombatListener`の2経路で、eliteの防御/回避/会心が**2回**適用される。2つの独立した監査が別々に同じ結論に到達 |
| **CMB-04** | モブの3つの乗算軽減枠すべてに `0.007/level` が掛かり、**Lv100で97.3%、Lv143で99.83%軽減**。枠ごとのcapは積に効かない |
| **CMB-05 / MOB-01** | モブHPの指数成長がバニラ `max_health` 上限1024で**無言飽和**。通常モブはLv19、eliteはLv28〜32以降HPが伸びない(スポーンから徒歩数分で到達する帯) |
| **CMB-07** | 装備で**816倍**(attack-power 63→51,408)、combatレベルは最大2.0倍。仕様書の「gear非依存ダメージ」原則が崩壊し、終盤は相互ワンパン |
| **CMB-08** | モブ攻撃力 `5.5×1.03^L`(19倍)に対しプレイヤー最大HPは48(2.4倍)。守備力が定数減算のため「床値1で無敵／帯を外すと即死」の**二値状態** |
| **CMB-06** | attack刻印eliteに対し**盾ブロックが完全に無効**(EliteMobsがBLOCKINGを0化 → TFが軽減済みダメージを破棄) |
| **PRG-08** | SP総供給の上限が **95** に対しノード総コストは **295**。取得可能なのは全体の約32%(排他考慮でも41%) |

> **PRG-08は私が再計算して裏を取りました。** POWERのEXP源は他スキルのレベルアップのみ(15スキル×Lv100×100EXP＝150,000EXP)。累積カーブ `9L²+809L=150,000` の解が L≈91.8 で、`max_level: 256` には**到達できません**。これが仕様通りの「取捨選択の設計」なのか、供給不足の事故なのかは**ユーザー判断が必要**です。
> **CMB-04/05/08と、進行中の「戦闘式リワーク」設計(`docs/design/`)との関係整理も必要**です。CMB-04〜08は現行実装の話で、リワーク後に自動解消するものと残るものが混在しています。

**削減見込み: 9,771行中およそ45〜50行(約0.5%)。**

このコードベースのコメントは既に「なぜ(Why)」に絞られた規律ある記述で、大半が仕様書参照付きです。私自身もサンプル検証しましたが、この結論を支持します。**大規模なコメント削減は、実施しても読み込み速度にほぼ寄与せず、代わりに「なぜその実装なのか」の根拠を失うリスクの方が大きい**と判断します。

### 「読み込み速度向上」に実際に効く代替案

ご要件の目的に照らすと、レバーは別の場所にあります。効果の大きい順:

1. **リポジトリ内の非成果物ディレクトリ(ORC-09)** — `.native-smoke/` 281MB、`external/` 65MB、`decompile/` 48MB(**7月以降1ファイルも更新なし**)、`source/` 12MB(同1ファイル)。全文検索・grep・AIの読み込みノイズに直結します。**コメント削減より桁違いに効果が大きい**見込み。削除可否はユーザー判断。
2. **巨大ファイルの分割** — `TrinityForge.java` 1,300行、`CombatListener.java` 929行、`ItemStatsConfig.java` 898行。いずれもご自身のコーディング規約(`~/.claude/rules`)の「800行上限」を超過。listeners パッケージは63ファイルで責務も分散しています。
3. **yml のコメント(1,568行)を `docs/` へ移設** — ただし後述の理由で**削除ではなく移設**にすべきです。

### yml のコメントは別扱いにすべき (ORC-04 / ORC-08)

`config-editor` の保存処理(`lib/yamlio.js:48-58`)は `YAML.stringify` で再シリアライズし、**先頭ヘッダのコメントだけ**を貼り直します。本文途中のコメントは復元されません。つまり**エディタで1回保存しただけで、そのファイルのコメントは消えます**。

yml のコメントは Java と違い**運用者(ご自身)が読む設定ドキュメント**です。例えば `combat/mob-level-table.yml` はコメント約60行＋コメントアウトされた設定例10行に対し、実設定は2行だけ。ここを消すと設定方法が分からなくなります。

→ 推奨: **`docs/` に設定リファレンスを作って移設し、yml には1行のリンクだけ残す。** これなら「読み込み速度」「エディタ保存で消える問題」「設定方法の可読性」が同時に解決します。あるいは `yaml` パッケージの Document API に移行してコメントを保持する方針も取れます。**どちらを採るかご判断ください。**

## 4. 私が訂正した点 (エージェント所見の検証結果)

監査の質を担保するため、影響の大きい主張は自分で再検証しました。

- **base-stats のステータスキー39件がJavaから参照されていない** → **私の誤検知でした。** ymlはケバブケース、Java側は `StatKeys.canonical` によるスネークケース(`loot-luck` → `loot_luck`)。全キーに消費側が存在します。この筋は取り下げます。
- **PRG-08 の上限SPは259ではないか** → **私の計算が誤りでした。** POWERは`max_level: 256`に到達できず、正しくは約92レベル/95SP。エージェントの数値が正しいことを確認しました。
- **GTH-02「連鎖破壊にガードが無い」** → 半分正しい。ドロップテーブル抽選側(`onBlockBreakDropTables`)には `placedBlockTracker.isPlaced` ガードがありますが、**連鎖破壊トリガー側(`onBlockBreak`)には無い**ことを確認しました。
- **INT-02「仕様書が実装と矛盾」** → 矛盾自体は事実ですが、これは「仕様書が誤っている」のではなく**進行中の戦闘式リワーク設計が先行して文書化され、実装が追随していない**状態と読むのが妥当です。

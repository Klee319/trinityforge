# スキルツリー草案 作成ブリーフ（共有）

このファイルは、`skilltree/職業別草案_*.md` を書くための共通の前提条件。**必ず全部読んでから書き始めること。**

---

## 1. 出力フォーマット（ユーザー指定・厳守）

```
職業名：テスト
プレステージ内容：テストポイント+1　※テストポイント：テストの点数が上がる

・A:アクティブスキルXX解放　※XXはS秒ごとに発動
　・A-1:...
```

読み取るべき決まり:

- `職業名：` は**日本語の役職名**（ファイル名 `light_weapons` ではなく「軽量武器」）
- `プレステージ内容：` は**周回報酬**。`※` で聞き慣れない語を必ず補足する
- `・A:` `・B:` … が**主軸**（A=Lv10 / B=Lv30 / C=Lv50 / D=Lv70 / E=Lv90）
- `　・A-1:` は**全角スペース1つ**で字下げした枝ノード
- `※` は**そのノードの補足説明**。プレイヤーが読んで意味が分かる言葉で書く
- ギリシャ路線は `・A-α-1:` のように書き、**排他であることを明記する**

各行は**プレイヤーに見せる文言**として書く。内部キー名（`crit_chance` 等）を本文に出さない。
ただし**各ツリーの末尾に「実装メモ」節**を設け、そこには使う stat キー・feature id・想定値を書く。

## 3. 使えるもの・使えないもの（2026-07-26 時点の確定情報）

### 3-A. `feature:` に書ける機構（Java 実装済み・全26種。これ以外は書かないこと）

```

spawner-silktouch-harvest  tree-fell  vein-mining  weapon-coating-unlock
wood-repair-unlock  xp-bottle-store-unlock
```

他に `glyph:<id>` / `brew:<id>` / `trade:<職業>` / `drop:<表>` / `overenchant:<id>` が使える。

### 3-B. アクティブスキルについて（**重要**）

ユーザーの書式例が「アクティブスキルXX解放」で始まっているが、**現状アクティブスキルは1本しかない**。

- **基盤は実装済み**: `com.trinityforge.active`（`ActiveSkillRegistry` / `ActivationDispatcher` /
  `CooldownManager` / `FeedbackLayer`）＋ `/tf active <id>` コマンド
- **登録済みのアクティブは `haste-active-mining` の1本だけ**（`HasteActiveSkill.java`）。
  `mining.yml` と `digging.yml` で `feature:haste-active-mining` として配られている
- **新しいアクティブを増やすのは Java の新規実装が要る**（基盤があるので1本あたりは軽いが、ゼロではない）

したがって:
- **既存の `haste-active-mining` は自由に使ってよい**
- **新規アクティブを提案してよいが、その行に必ず `【要実装】` と付けること。**
  実装済みのものと区別が付かない草案は受け付けない
- 各ツリーに無理にアクティブを入れないこと。**入れる意味がある所にだけ入れる**

### 3-E. 効率の統合

`gathering-efficiency`（表示名「**採集効率**」。2026-07-27 に「最終効率」から改称）に一本化され、**上限が撤廃**された。
メインハンドの農業/採掘/伐採/切削の道具に、効率強化エンチャントのレベルとして反映される。

⚠️ **バニラの採掘速度は効率レベルの `レベル² + 1` で伸びる。10 前後で大半のブロックが即破壊。**
**1ツリーの全帯合計が 5 を超えないように配ること。**

## 4. 必ず守る設計ルール

### ルール1 — プレステージに必ず**具体的な数値と stat キー**を書く

現状 **6ツリー（alchemy / smithing / enchanting / farming / fishing / woodcutting）で
プレステージが文言だけで `buffs` が空＝実際には何も起きない。** これを埋めるのが今回の最優先事項。

さらに mining / digging は「採掘速度+1」と書いてあるのに速度分の buffs が無く、
ars_smithing は「必要ソース-10%」が無く、power は `enabled: false` で無効。

**担当ツリーのプレステージは、実装メモに `buffs:` の具体的な yml 断片まで書くこと。**

### ルール2 — ギリシャ路線は「レーン固定」にする

現状 `group: A-greek` 〜 `E-greek` で**帯ごとに排他**になっているが、
`parent` が主軸を向いているため**帯ごとに選び直せてしまい、5帯通すと全員似た配分になる**。

**草案では `B-α-1 の親を A-α-1 にする**（＝A帯で選んだ路線を最後まで通す）形で書くこと。
文言としては「※αを選ぶと以降もα路線のみ進めます」のように、プレイヤーに分かる形で明示する。

### ルール3 — 3路線は「性格」を分ける（同じ物の3段階にしない）

現状の戦闘ツリーは α=ダメージ / β=会心率 / γ=会心ダメージ で、**どれも火力**。
選ぶ意味が薄い。「攻める型」「削る型」「耐える型」のように**役割が変わる**ようにする。

### ルール4 — 率のステータスの書き方

`PercentStatNormalize.coerce` の実際のルール（コードで確認済み）:

| 書いた値 | 解釈 |
|---|---|
| `0.2` | **20%**（1.0以下はそのまま分数として扱われる） |
| `20` | **20%**（2〜100の整数は「%表記」とみなして /100 される） |
| `1` | ⚠️ **100% ではなく 1.0（＝100%相当）のまま。** 境界なので使わないこと |
| `1.2` | 120%（非整数はそのまま） |

**つまり `0.2` と `20` はどちらも正しく20%になる。** 既存ファイルの周囲の書き方に合わせること
（戦闘ツリーは `crit-chance: 0.1` のように分数、他は整数%が多い）。

⚠️ 本当の事故要因は**二重正規化**（同じ値を2回 coerce に通す）。
実際にこれで巣の採集ボーナスが設定値の 100分の1 になっていた。**同じ値を2箇所に書かないこと。**

⚠️ `crit-damage` は **RATE_KEYS に入っていない**（`10` = +1000% が意図的に許されている）。
`crit-damage: 0.3` は 30% だが `crit-damage: 30` は **3000%** になる。ここだけ分数で書くこと。

### ルール5 — 主軸は「必ず通る道」、枝は「個性」

主軸 A〜E は全員が取るので、**取り逃しが起きて困る物（解放・基礎数値）を置く**。
枝には尖った物・ギミックを置く。

### ルール6 — 既存ノードは**構造を壊さず中身を差し替える**

ノードの数・Lv・位置は原則そのまま。「このノードの効果をこう変える」という形で書く。
構造ごと変えたい場合は、**なぜ変えるかを1行書くこと**。

## 6. 禁止事項

- **`D:\game\minecraft\` 以下には絶対に触らない**（実サーバー）
- **`TrinityForge/src/main/resources/skilltree/*.yml` を編集しない。** 今回は**草案(.md)を書くだけ**
- **`TrinityForge/` 配下の Java / yml を一切編集しない。** 別の作業者が同時に編集中
- 実装されていない機構を、実装済みのように書かない。**推測で feature id を作らない**
- 一次情報（`_現構造ダンプ.txt` と実 yml）に無いことを断定しない。
  分からないことは「要確認」と書いて残すこと
